# 마이그레이션 파일명 규칙 — 번호를 버리고 시각으로 짓는다

> 한 줄 요지: **새로 만드는 마이그레이션 파일의 이름은 `YYYYMMDDHHMMSS_이름.sql` 이다.** 예를 들어 `20260806131500_item_lifecycle_index.sql` 처럼, 파일을 만든 UTC 시각 열네 자리를 앞에 붙인다. `0090_...` 처럼 순번을 매기는 방식은 더 쓰지 않는다.

여기서 마이그레이션(migration)은 **데이터베이스의 구조를 바꾸는 SQL 스크립트**를 말한다. 표를 새로 만들거나, 열을 추가하거나, 제약을 거는 파일들이며 보통 `supabase/migrations/` 폴더에 쌓인다.

---

## 왜 이 규칙이 있나

### 실제로 일어난 사고

여러 Claude 세션이 서로 다른 브랜치에서 **동시에** 작업하다가, 같은 번호를 각자 집어 갔다. 두 세션 모두 저장소를 보고 "지금까지 `0083` 까지 썼으니 다음은 `0084` 다"라고 똑같이 옳게 판단했다. 그 결과 서로 다른 내용의 두 파일이 같은 번호를 갖게 됐다.

```
PR #198   supabase/migrations/0084_spec_fill_targets.sql
PR #199   supabase/migrations/0084_project_reference_single_target.sql
```

### 이 충돌이 위험한 이유는 git 이 잡지 못하기 때문이다

**이 문장이 이 규칙의 전부다.** 이것을 모르면 "충돌이 나면 알게 되겠지"라고 생각하고 옛 방식으로 돌아가게 된다.

git 이 충돌을 알려 주는 조건은 **같은 파일의 같은 자리를 두 브랜치가 다르게 고쳤을 때**다. 그런데 위 두 파일은 **이름이 서로 다르다.** git 이 보기에 이것은 서로 무관한 새 파일 두 개를 각자 추가한 것일 뿐이므로, 텍스트 충돌이 일어나지 않는다. 그래서 다음과 같은 일이 벌어진다.

1. 두 PR(풀 리퀘스트, 브랜치를 main 에 합쳐 달라는 요청) 모두 GitHub 에서 `mergeable_state = clean` 으로 보고된다. 즉 "합칠 준비가 됐다"고 초록불이 뜬다.
2. 두 PR 이 차례로 머지된다. 이 순간에도 아무 경고가 없다.
3. 머지가 끝난 **뒤에야** 저장소에 같은 번호를 가진 파일이 둘 있다는 것을 알게 된다.

즉 이 결함은 사고가 난 다음에 발견되며, 발견 시점에 이미 main 에 들어와 있다.

### 더 나쁜 두 번째 효과 — 적용되지 않은 것을 적용된 것으로 착각한다

번호가 겹치면 **어느 파일이 실제로 데이터베이스에 적용됐는지 이름만으로는 구분할 수 없다.** 라이브 데이터베이스의 적용 이력을 조회하면(`list_migrations`) `0084` 라는 항목이 하나 보인다. 그것을 본 사람은 자기 파일이 적용됐다고 읽지만, 실제로 적용된 것은 같은 번호를 가진 **다른 파일**일 수 있다.

그 결과가 무엇인지 정확히 말하면 이렇다. **걸리지 않은 제약이 걸린 것으로 보인다.** 오류 메시지는 나지 않는다. 데이터베이스는 조용히 제약 없이 돌아간다.

### 같은 일이 곧바로 한 번 더 일어났다

첫 충돌을 해소하려고 PR #199 가 번호를 `0085` 로 옮겼다. 그런데 라이브 데이터베이스에는 이미 `0085_switch_free_text_value` 가 적용돼 있었다. 저장소 파일 목록만 보고 고른 번호였기 때문이다. 번호를 안전하게 고르려면 **내 브랜치 · main · 라이브 이력 세 곳의 합집합**을 봐야 하는데, 이 세 곳을 매번 빠짐없이 확인하는 일은 사람도 에이전트도 안정적으로 해내지 못한다.

### 사람의 기억으로 막는 방식은 이미 실패했다는 증거

이 하나의 문제에 **네 개의 세션이 각자 부딪혔다.** 한 세션은 커밋 제목에 "번호 충돌 가드"를 달았고, 한 세션은 충돌을 두 번 만들었으며, 한 세션은 충돌을 발견하고도 "내 PR 과 무관하다"고 넘겼고, 네 번째 세션이 최종적으로 해소했다.

그 해소 과정에서 드러난 사실이 결정적이다. **한 세션이 번호를 바꾸면서 파일 이름 2개만 고치고, 그 번호를 가리키던 문서·코드 참조 17곳을 놓쳤다.** 개번(번호 바꾸기)은 파일 이름만 바꾸는 작업이 아니라 저장소 전체의 참조를 함께 옮기는 작업이고, 그래서 사람이 손으로 하면 빠진다.

## 규칙

### 1. 새 마이그레이션 파일의 이름은 `YYYYMMDDHHMMSS_이름.sql` 이다

앞의 열네 자리는 **파일을 만드는 시점의 UTC 시각**이다. 순서대로 연(4) · 월(2) · 일(2) · 시(2) · 분(2) · 초(2) 를 붙여 쓴다. 그 뒤에 밑줄 하나를 두고, 무엇을 하는 마이그레이션인지 알 수 있는 이름을 영문 소문자와 밑줄로 적는다.

열네 자리를 손으로 세지 말고 명령으로 얻는다.

```bash
date -u +%Y%m%d%H%M%S
# 예: 20260806131500
```

그러면 파일 경로는 이런 모양이 된다.

```
supabase/migrations/20260806131500_item_lifecycle_index.sql
```

### 2. 왜 번호가 아니라 시각인가

세 가지 이유로 이 방식을 택했다.

**첫째, 충돌을 잡는 것이 아니라 없앤다.** 번호 방식에 자동 검사를 붙여도, 검사는 충돌이 *생긴 뒤에* 잡는 장치다. 세션은 여전히 충돌을 만들고, 매번 개번 작업이 따라온다. 그리고 앞에서 본 것처럼 개번은 참조 17곳을 놓칠 수 있는 위험한 작업이다. 시각을 쓰면 두 세션이 **같은 초에** 파일을 만들지 않는 한 애초에 겹칠 일이 없다. 검사할 것 자체가 사라진다.

**둘째, 번호는 확인해야 알 수 있지만 시각은 확인할 필요가 없다.** 번호를 고르려면 다른 곳에 무엇이 있는지 조회해야 하고, 그 조회 대상이 세 곳(내 브랜치 · main · 라이브)이라 하나만 빠뜨려도 틀린다. 시각은 아무것도 조회하지 않고 혼자 결정할 수 있다. **다른 브랜치가 무엇을 하고 있는지 알 필요가 없는 것**이 이 방식의 핵심 이점이다.

**셋째, 도구와 싸우지 않는다.** Supabase CLI(커맨드라인 도구)가 마이그레이션 파일을 만들 때 쓰는 기본 형식이 바로 이 열네 자리 시각 형식이다. 라이브 데이터베이스의 적용 이력도 이미 `version`(20260806053342 같은 시각)과 `name` 을 따로 갖고 있다. 즉 이 형식은 도구가 이미 기대하는 형식이다.

### 3. 무엇을 포기하는지도 알고 택했다

정직하게 적는다. **순번 감각을 잃는다.** `0083` 다음이 `0084` 라는, 파일 이름만 보고 "몇 번째 마이그레이션인가"를 아는 감각이 없어진다.

이 대가를 감수할 만하다고 판단한 근거가 있다. **번호는 이미 순서를 뜻하지 않았다.** 번호 방식에서도 여러 브랜치가 병렬로 번호를 집어 갔기 때문에, 실제 적용 순서는 번호 순서와 달랐다. 반대로 시각은 정의상 만든 순서를 뜻한다.

또한 파일 이름을 사전순으로 정렬하면 두 형식이 섞여 있어도 순서가 깨지지 않는다. 실제로 정렬해 보면 이렇게 된다.

```
0001_init.sql
0089_npi_condition_exempt.sql
20260101090000_bar.sql
20260806131500_foo.sql
```

네 자리 번호는 `0` 으로 시작하고 열네 자리 시각은 `2` 로 시작하므로, **기존 번호 파일 전체가 항상 신규 시각 파일보다 앞에 온다.** 그리고 시각 파일끼리는 사전순이 곧 시간순이다. 즉 사전순 정렬이 그대로 적용 순서가 된다.

### 4. 기존 번호 파일은 개번하지 않는다

이미 저장소에 있는 `0001_...` ~ `0089_...` 형태의 파일은 **그대로 둔다.** 새로 만드는 파일만 시각 형식으로 짓는다. 그래서 한동안 두 형식이 한 폴더에 섞여 있게 되는데, 그것이 의도된 상태다.

개번하지 않는 이유는 두 가지다.

1. **라이브 이력과의 대응이 오히려 더 어긋난다.** 라이브 데이터베이스의 적용 이력에는 옛 이름이 적혀 있다. 파일 이름을 바꾸면 이력에 적힌 이름과 파일 이름이 갈라지고, "이 파일이 적용됐는가"를 이름으로 대조하는 일이 불가능해진다.
2. **문서와 코드의 참조가 함께 깨진다.** 마이그레이션 번호는 파일 이름에만 있지 않다. 설계 문서, 절차 문서, 주석, 다른 마이그레이션의 설명이 그 번호로 서로를 가리킨다. 앞에서 본 사고가 정확히 이것이다 — 파일 2개를 고치고 참조 17곳을 놓쳤다. 파일 89개를 개번하면 놓치는 참조는 훨씬 많아진다.

### 5. 적용할 때 넘기는 이름 규칙은 그대로다

이 규칙은 **파일 이름을 어떻게 짓는가**만 바꾼다. **적용 절차는 하나도 바뀌지 않는다.**

특히 다음 규칙이 그대로 유지된다. 마이그레이션을 적용할 때(`apply_migration`) 넘기는 `name` 값은 **파일 이름에서 `.sql` 만 뗀 것과 글자 하나까지 같아야 한다.** 이것이 저장소의 파일 목록과 라이브의 적용 이력이라는 두 장부를 일치시키는 장치이기 때문이다.

파일 이름이 시각 형식이 되면 `name` 도 그 시각을 그대로 포함한다.

| 파일 | `apply_migration` 에 넘기는 `name` |
|---|---|
| `20260806131500_item_lifecycle_index.sql` | `20260806131500_item_lifecycle_index` |

시각 열네 자리를 빼거나, 뒤로 옮기거나, 이름 쪽만 넘기는 것은 모두 규칙 위반이다.

### 6. 도입할 때 저장소마다 한 가지를 확인한다

이 규칙이 동기화로 새 저장소에 내려갈 때, 그 저장소에 **파일 이름이 네 자리 번호로 시작하는지 검사하는 자동 장치**가 이미 있을 수 있다. 번호 방식을 지키게 하려고 만든 검사이므로, 그 검사는 시각 형식 파일을 "번호 접두어가 없다"며 거부한다.

그런 검사가 있으면 **첫 시각 형식 파일을 만들기 전에 그 검사가 두 형식을 모두 받아들이도록 고쳐야 한다.** 고치지 않으면 규칙을 지킨 PR 이 검사에 막힌다. 이 확인은 저장소마다 사람이 한 번 해야 하는 일이다. 자동 검사는 `.github/workflows/` 에 있고, 그 폴더는 동기화 봇이 내려보내지 않기 때문이다.

## 적용 범위

- 이 규칙은 **데이터베이스 마이그레이션 파일을 두는 저장소**에 적용된다. 그런 파일이 없는 저장소에서는 해당되는 상황이 오지 않는다.
- 이 규칙의 **단일 원본은 창고(Template-repository)의 `.claude/rules/migration-naming.md`** 다. 여기서만 고치고, 나머지 저장소에는 동기화 봇이 내려보낸다.
- `.claude/rules/*.md` 는 Claude Code 세션 시작 시 자동으로 읽히므로, 각 저장소에서 이 파일을 따로 불러오는 설정을 넣을 필요가 없다.
- 저장소마다 마이그레이션 **적용 절차** 문서를 별도로 두는 경우, 그 문서의 파일명 관련 서술은 이 규칙에 맞춘다. 절차(어떤 도구로 적용하는가, 이름을 어떻게 넘기는가)는 그 문서가, 파일명 형식은 이 규칙이 정본이다.
